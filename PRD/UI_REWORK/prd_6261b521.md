# PRD: Legendarium Explorer – Preview UI Rebuild

## Document Version
- **Version:** 1.1
- **Last Updated:** 2026-07-25
- **Status:** Draft

---

## 1. Objective

Rebuild the **Preview UI** of Legendarium Explorer from scratch as a clean, production-ready interface.

Treat the current implementation (/preview) as a **behavior reference only** (POC), not as an architectural baseline.

The result must prioritize clarity, consistency, stability, and maintainability over patch compatibility.

---

## 2. Product Context

The Preview page is the core exploration surface for a rendered genealogy graph.

Users need to:

- Inspect the graph quickly
- Filter and find people efficiently
- Run two-person selection + LCA analysis
- Understand graph semantics via legend
- Switch view/theme modes without layout side effects

The experience must feel deliberate and calm, not improvised.

---

## 3. Technical Stack

### Framework
- **Vite + React + TypeScript** (existing POC stack, maintained)

### Recommended Libraries
- **shadcn/ui** – Modular UI components (Panels, Dropdowns, Toggles, Buttons)
- **Radix UI** – Headless accessible primitives (Dialogs, Flyovers, Popovers)
- **Allotment** – Resizable split panes (Main panel layout)
- **Lucide Icons** – Consistent icon set (Tool controls, navigation)
- **react-i18next** – Internationalization framework

> Alternatives are permitted if justified. No custom-building where an established library exists.

### Internationalization (i18n)
- i18n structure must be prepared from the start (t() function, locale files)
- Only `en.json` is populated in v1
- Adding a new language = adding a new JSON file, no code restructuring required

### Persistence
- User settings (selected theme, panel states open/minimized, last filter, preferences) are persisted via **LocalStorage**
- On reload, the UI restores the user's last state

The application uses a global **hamburger menu** accessible from a button in the **top-left page header**. The menu opens as an **overlay** that covers all content (including panels) and closes on:
- Menu item selection

## 6. Sub-Panels (within Tree Canvas)

### 6.1 Design Principle

**Left = Action / Search | Right = Information / Results**

### 6.2 Left Sub-Panel: Filter, Search & Selection

#### Filter Section
- Grouped categorical filters: **House, Species, Gender, Era** (at minimum all filterable attributes in dataset)
- Filter logic: User can toggle between **AND / OR** combination
- Quick **"Clear/Reset"** action
- Match counter visible (e.g., "12 matches")
- **"Show in tree" checkbox**: When active, non-matching nodes are dimmed/hidden in canvas. When inactive, filter results are shown only in the panel without affecting the canvas view.

#### Search Section
- Full-text search input across all attributes (Name, House, Species, Era, etc.)
- Result list with compact context (name + short metadata)
- Selecting a search result **focuses** the corresponding person in the graph (pan + highlight)
- Each result has **"Add as A" / "Add as B"** buttons for selection

#### Selection Section
- Current selection counter/state (Person A: ___, Person B: ___)
- Visual guidance for first/second selection
- **"Fade unrelated" control**: Dropdown with options "Dim" (reduced opacity) or "Hide" (completely hidden)
- Clear selection button

### 6.3 Right Sub-Panel: Inspector & LCA

#### Inspector Section
- Stable **empty state** when no person is selected
- When **1 person selected**: Full panel height for person details (all available metadata)
- When **2 persons selected**: Panel split equally for Person A and Person B
- Key metadata: Name, Gender, Species, Birth, Death, House, Era, etc.
- **"Add as A" / "Add as B"** buttons (redundant path, also available in search results)

#### LCA Section (below Inspector)
- Visible when 2 persons are selected
- LCA result output (Lowest Common Ancestor)
- Number of generations between A → B
- Additional analysis results as available from POC logic

### 6.4 Panel Interaction Model

All sub-panels support:
- **Minimize/Restore** (minimize to upper-left / upper-right respectively)
- **Docked default** behavior (left panel docked left, right panel docked right)
- **Optional undocked repositioning** (drag to reposition within canvas area)

Constraints:
- No overlap in normal docked states
- No clipping outside the intended workspace
- No drift across resize/theme/mode changes
- Undocked movement remains constrained within the tree canvas area

## 8. Theme System

### 8.1 Two Independent Themes

| Theme | Governs | Scope |
|-------|---------|-------|
| **Page Theme** | Page header, hamburger menu, subpages (Impressum, Disclaimer), surrounding chrome | Global, all pages |
| **Tree Theme** | Tree canvas, sub-panels (Filter, Search, Inspector, LCA), legend, tool controls | Family Tree page only |

Both themes are **independently configurable**. A user can have Dark Page + Light Tree (or any combination) for optimal readability.

### 8.2 Theme Controls Placement

```
Page Level (visible on ALL pages):
┌─────────────────────────────────────────────────────────────────────┐
│ [☰] Legendarium Explorer                    [☀/☽] [▼Theme] [✎]     │
│                                              ^── Page Theme ────^   │
└─────────────────────────────────────────────────────────────────────┘

Tree Level (visible only on Family Tree page, within tool bar):
┌─────────────────────────────────────────────────────────────────────┐
│  [↺] [⛶] [↔] [F11]  [📷▼] [📄]         [☀/☽] [▼Theme] [✎]       │
│                                           ^── Tree Theme ────^      │
└─────────────────────────────────────────────────────────────────────┘
```

### 8.3 Theme Options

Each theme (Page and Tree) supports three modes:

1. **Light / Dark** – Base toggle
2. **Thematic Presets** – Selectable from a dropdown (e.g., Tolkien, Gondor, Rohan, Mirkwood, Imladris)
3. **Custom (Own)** – User-defined via the theme editor

### 8.4 Theme File Architecture

Thematic themes are managed in a **dedicated theme folder**. Each theme is a self-contained file (CSS or TS). New themes can be added by creating a new file + registry entry, without modifying existing code.

```
/src/themes/
  ├── tree/
  │   ├── tolkien.theme.[css|ts]
  │   ├── gondor.theme.[css|ts]
  │   ├── rohan.theme.[css|ts]
  │   ├── mirkwood.theme.[css|ts]
  │   ├── imladris.theme.[css|ts]
  │   └── index.ts  ← Registry
  ├── page/
  │   ├── tolkien.theme.[css|ts]
  │   ├── ...
  │   └── index.ts  ← Registry
  └── types.ts  ← Shared theme type definitions
```

> The format must be consistent for both presets and user-custom themes.

### 8.5 Custom Theme Editor (Flyover)

Opens as a slide-over panel. Must be:
- Clearly tied to the corresponding theme context (page or tree)
- Clearly openable (pencil/gear icon)
- Clearly dismissible (close button + click outside)
- Free from ambiguous state (user must always know which theme they are editing)

#### v1 Scope:
- **Colors**: Background, text, accent, node colors, line colors (via color picker)
- **Typography**: Font size, font family

> Designed to be extensible in later versions (e.g., geometric aspects like border-radius, line-width, spacing).

#### Theme Editor State:

### v1 Strategy: Canvas First (Graceful Degradation)

- **>= 1024px (Desktop)**: Full layout as designed (all panels visible by default)
- **< 1024px (Tablet/Mobile)**: Sub-panels start in **minimized state**. User can expand on demand. Tree canvas occupies full viewport by default.

> Full mobile-optimized layouts (bottom-sheets, tabs, dedicated mobile patterns) are planned for a later phase. The minimize/restore system built for desktop serves as the foundation.

## 12. Visual Geometry Language

The shape language for primary surfaces must be coherent:
- Edges aligned to workspace boundaries: **crisp/intentional**
- Corners facing into free workspace: **subtly rounded**
- No inconsistent corner impressions between panels
- Sub-panels must feel like they belong to the tree canvas area, not float randomly

---

## 13. Loading State

- Display a **spinner** while the tree is loading
- Must not interfere with existing tree render logic
- If spinner integration conflicts with render pipeline, the implementing agent may choose an appropriate alternative (e.g., skeleton, progress indicator)

---

## 14. Non-Goals

- No redesign of the tree renderer (nodes, lines, layout remain as POC)
- No requirement to preserve existing Preview layout code structure
- No pixel-perfect copy of current POC
- No new business features beyond current Preview scope
- No Undo/Redo in v1 (planned for later)
- No full mobile-optimized layout in v1

---

## 15. Acceptance Criteria (Product Level)

The rebuilt Preview is accepted when all are true:

1. Panel and control placement remains stable across common user flows
2. Sub-panels do not protrude outside intended tree canvas workspace
3. Theme split (tree vs. page) is visually and behaviorally unambiguous
4. Legend remains compact and non-disruptive while still informative
5. Theme editor flyovers are reliable to open/close and clearly contextual
6. The interface reads as one coherent system, not a patched composition
7. Global Statistics panel displays tree analysis metrics correctly
8. Filter <-> Canvas interaction works correctly (with "Show in tree" toggle)
9. Selection + LCA workflow functions end-to-end
10. Export PNG (visible + full) functions correctly
